# Pastrack web · Beego

A separate Beego application for the existing Pastrack MySQL schema. Monitoring dashboard with master-data administration and XLSX/PDF reporting: devices, latest location/map, GPS position history, raw message inspection, device events and BLE report capture. Timestamps render in Asia/Jakarta. The fuel screen explicitly identifies unverified decoding; it does not invent liters or connectivity status.

## Run locally

Go 1.27.3+ (see go.mod for the selected toolchain). Configure environment from `.env.example`, then `go run .`. `SESSION_SECRET` must be random and at least 32 characters. Initialize the account/session schema and admin via the DBA migration described below. The application does not load dotenv files itself. All application and API routes require login, except login, static assets, and a minimal health endpoint. Login sessions last 12 hours, use HMAC-signed HttpOnly SameSite cookies, and login attempts are limited. For HTTPS deployments set `COOKIE_SECURE=true`. Trust only your reverse proxy; bind locally by default.

## Master CRUD and enterprise report module

New sidebar sections: **Master kendaraan**, **Master perangkat**, **Laporan**, and **Jejak audit**.

- Master create/edit supports plate, vehicle name/type/fleet/status; IMEI/model/protocol/firmware/vehicle assignment/JSON metadata/status.
- Duplicate plates and IMEIs are rejected, including archived identities. IMEI changes are blocked when history exists; register a replacement as a new device.
- Delete is a reversible archive: sets `deleted_at`, deactivates the master, and retains all historical data. Vehicles with non-archived devices must have devices reassigned or archived first. Restore returns the record as inactive so an administrator explicitly decides activation. These changes do not send commands to physical trackers.
- `row_version` protects concurrent edits. Changes and before/after audit records commit in one transaction. Mutations require authenticated sessions, a CSRF header, matching Origin, bounded JSON, and server-side validation.
- Runtime DB identity is now `pastrack_web_app`: SELECT on the application schema, INSERT/UPDATE on the two master tables, INSERT on the audit log. No runtime DDL, DELETE, or audit UPDATE permissions. The deployed DB schema is `pastrack`; the original receiver's default `gps_tracker_rnd` is only a configurable fallback.

### Reports

Five report types: GPS positions, device events, reception/raw messages, vehicle master, device master. The report form supports WIB start/end dates, device, vehicle and applicable status. Operational periods use received time (fallback to creation time if a linked raw record is unavailable), start-inclusive and next-day-end-exclusive. Master exports are current snapshots, exclude archived rows, and explicitly ignore the operational period. Historical vehicle labels follow current master assignments and are documented as such.

Every file has its own Report ID, generation timestamp, actor, filters, source/metric definitions and snapshot-consistent summary/details. Preview shows up to 50 detail rows and explicitly states total rows. XLSX/PDF downloads use the complete filtered dataset within limits, not the preview rows. Separate downloads are independent snapshots and receive different Report IDs.

- XLSX: summary, detail and definitions sheets; typed numeric/date values; text IMEI (leading zeros retained); literal user text (formula injection prevented); seven-decimal coordinates; table filters, striped rows, frozen headers, repeat print titles, A4 landscape/page headers/footers.
- PDF: branded A4 landscape cover with scope and metrics, repeated table headers, wrapped cells, complete long-payload appendices, page x of y, internal classification and WIB timezone labels.
- Mean speed is an arithmetic mean of valid samples, not trip-average speed. Fuel liters, consumption and travel distance are not invented from incomplete data.
- Maximum period 366 days; up to 50,000 XLSX rows / 5,000 PDF rows; two report jobs at once. Oversized requests fail explicitly, with no silent truncation. Very long payloads exceeding Excel's per-cell capacity are rejected rather than truncated.
- Export audit captures filters, total row count, summary, Report ID, format and SHA-256 digest. UI audits are read-only; this is an application audit trail, not an external tamper-proof ledger.

## Vehicle behavior analytics

Dashboard → Kendaraan now uses GPS-time periods (24 hours / 7 days / 30 days). Ranking switches between estimated GPS distance and observed moving duration. Cards show observed moving vehicles, distance, moving hours, duration-weighted moving speed, vehicles with data and registered vehicles. Daily distance and hourly moving vehicle-hours use WIB, splitting intervals at hour/day boundaries.

Only valid coordinates and speeds 0–200 km/h are used. Same-device duplicate GPS timestamps contribute once. Distance sums all valid straight-line segments, independently of reported device speed, with continuity up to 30 minutes and implied speeds up to 200 km/h (matching Tracking). Durations only classify intervals up to five minutes: movement uses both endpoint speeds >3 km/h, or spatial movement ≥20 m with implied speed >3 km/h; stationary intervals require both endpoint speeds and spatial speed ≤3 km/h. When coordinates imply movement despite low device speed, the average uses spatial speed and exposes the inferred interval count. Other unclassified durations remain unknown. The sample-device maximum remains the maximum reported valid speed.

Distance is an estimate, not an odometer or road distance. Observed stationary time does not imply ignition state. Coverage is classified observed duration / selected period; absent data is explicitly distinguished from stationary behavior. With multiple reporting devices, the device with most valid unique samples is selected (lowest ID breaks ties), using current vehicle assignments. The query refuses periods exceeding 250,000 source points rather than silently truncating. Other dashboards retain their existing definitions.

## Synchronized fleet playback

Tracking → Putar works for one vehicle and the entire fleet. `tracking-playback.js` owns one GPS-time cursor across the requested start/end, independently looking up each vehicle's bounding samples by binary search. An individual labeled car icon follows each route, with heading, displayed speed and observed moving/stopped status. Position/heading/speed interpolate only across connected fixes no more than five minutes apart. During GPS gaps the marker stays at the last recorded location with a gap label; before the first sample it stays hidden, and after the last sample it remains explicitly labeled as last GPS. Out-of-period fallback positions stay muted and do not animate. Origin/destination filtering continues to restrict the per-vehicle histories used for replay.

Controls provide play/pause, restart, seek and explicit rates (1 minute, 10 minutes, 1 hour, 6 hours or 1 day of GPS time per real second). Default rate scales with the period. requestAnimationFrame advances the clock using elapsed wall time, with per-frame stall limits, shared timestamps and no network calls.
